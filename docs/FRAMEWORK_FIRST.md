# 框架优先工作流

## 触发条件

任何新功能、重构、迁移、插件、服务器部署或架构调整。

## 强制顺序

```text
需求
→ 写 BRIEF
→ GPT/WorkBuddy 产出 Markdown 框架
→ 审查框架
→ 列验收项
→ 实现
→ 测试
→ 部署
→ 文档/版本
```

## 1. 写 Brief

使用 `docs/FRAMEWORK_BRIEF.md`。

必须包含：

```text
目标
非目标
当前基线
相关文件/模块
接口与数据边界
旧功能保留清单
验收命令
风险
禁止事项
```

## 2. 找 GPT/WorkBuddy

要求对方输出一个完整 Markdown 文件，不允许只给聊天摘要。

如果 WorkBuddy/GPT 不可用：

```text
新开一个全新上下文的 session
只让它做架构/任务书
明确禁止它直接改代码
要求输出 Markdown
```

## 3. 审查框架

至少检查：

```text
是否覆盖现有功能
是否会双回复/双写/双重模型调用
是否保留配置/data/会话
是否有回滚
是否有可执行测试
是否有阶段 commits
是否明确旧入口逐个关闭
```

## 4. 实现

框架通过后才开干。

每阶段：

```text
先隔离实例验证
再测试分支
最后生产
```

## 5. 完成标准

```text
代码
测试真实通过
文档更新
版本更新
回滚路径
服务器验证
```

## 禁止

```text
跳过框架直接写代码
把旧插件整体复制成兼容核心
把最小占位包称为完成
未验证就切生产
让用户手动 capture/改配置来补自动化缺口
```
